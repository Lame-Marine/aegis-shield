# Devices, game updates and recovery

## Which device (aegis/device.py)
- `config/device.json` `{"serial": ...}` picks the device; `device.ALLOWED` holds only the Aegis devices: `<phone-ip>:5555` (Galaxy S10 SM-G973F, Android 12, no root, USB serial <phone-usb-serial>: Aegis's home) and `emulator-5554` (LDPlayer 0, SM-S9110, root). run.py, covert.py, sweep.py, build_reader.py and watchdog.py import SERIAL/MODEL/ROOT from it. Never add the owner devices (emulator-5556, BlueStacks, his phone).
- Switching devices: an account can be logged in on ONE device; a second login kicks the first. Before anyone logs Aegis in elsewhere, stop bot.py + watchdog.py and force-stop the game on the old device; then change device.json, install the reader on the new device, start bot + watchdog. Shut LDPlayer 0 down when the phone is in use (frees ~6 GB RAM): `ldconsole quit --index 0`.

## Phone specifics (S10)
- adb over Wi-Fi: `adb -s <phone-usb-serial> tcpip 5555`, then `adb connect <phone-ip>:5555`. TCP mode is lost on every phone reboot; it needs one USB connection (the user may have to accept the 'Allow USB debugging' RSA prompt; 'unauthorized' in `adb devices` = prompt pending). The USB port is flaky: run everything over Wi-Fi.
- No root needed: on Android 12 (FUSE) files adb writes into `/sdcard/Android/data/com.phs.global/files` get the game's uid and mode 660, so game updates can overwrite them.
- Unity stops when the screen is off or the game is in the background: keep 'stay awake while charging' on (`settings get global stay_on_while_plugged_in` = 7), the watchdog wakes the screen and brings the game to the front.
- VPN: official WireGuard APK from download.wireguard.com/android-client (no Play Store needed), import the user's `.conf` through the app's file picker (drive UI with `aegis/phone_ui.py` by text/id), delete the copied conf from Downloads, then `settings put secure always_on_vpn_app com.wireguard.android` + `always_on_vpn_lockdown 1`. Verify the game's traffic uses the tunnel: `ip route get 1.1.1.1 uid $(stat -c %u /sdcard/Android/data/com.phs.global)` -> `dev tun0`, and tun0 counters in `/proc/net/dev` rising. Each device needs its own WireGuard key.
- Installing the game without Play Store: pull the split APKs from a device that has it (`pm path com.phs.global`, `adb pull` each) and `adb install-multiple base.apk split_*.apk`; a copy signed differently must be uninstalled first.
- What must stay on: only the phone (screen on, game in front, Wi-Fi, charger); bot + watchdog run on it in Termux (below). The PC is only needed to deploy updates and after a phone reboot.

## Hosting bot + watchdog in Termux on the phone
the owner chose the phone over the Pi: the Pi runs the other services, and Aegis code stays off that machine.
1. Install Termux + Termux:Boot from their GitHub releases (both `+github` builds: they must share a signing key): `adb push x.apk /data/local/tmp/` then `adb shell pm install -r` (plain `adb install` over Wi-Fi can hang on the verifier). If the package verifier refuses (`INSTALL_FAILED_VERIFICATION_FAILURE`), set `settings put global verifier_verify_adb_installs 0` for that one install and restore the previous value (delete the key if it was null). Then `dumpsys deviceidle whitelist +com.termux` (+ `.boot`) and `cmd appops set com.termux RUN_ANY_IN_BACKGROUND allow`.
2. Stop the PC watchdog before typing into Termux: Termux in front backgrounds the game and the watchdog keeps yanking it back.
3. Open Termux once (bootstrap), type `termux-setup-storage`, accept. Drive it by pushing scripts to `/sdcard/Download/` and typing only `bash /sdcard/Download/x.sh` (`input text` with `%s` for spaces): `;`, `>`, `&`, quotes get mangled when typed. Scripts write their output to a log in Download, read back with `adb shell cat`.
4. Packages: pin `deb https://packages-cf.termux.dev/apt/termux-main stable main` in `$PREFIX/etc/apt/sources.list` (the random mirror can answer 429), then `apt-get install python android-tools termux-tools`. UnityPy for reader rebuilds: `apt-get install python-pillow clang make cmake binutils` + `pip install UnityPy` (~5 min).
5. Termux's adb to the phone itself: `adb connect 127.0.0.1:5555` (needs `adb tcpip 5555` still active) raises the 'Allow USB debugging?' prompt for Termux's key: tick `sec_alwaysUse`, press `button1` via `aegis/phone_ui.py`. If the first connect timed out before Allow, the prompt comes back: accept again. Inside Termux adb also lists that port as `emulator-5554`: never use that name there.
6. `python aegis/deploy_phone.py --first` (PC) drops the bundle + `phone_install.sh` in Download; run it in Termux. Layout: `~/aegis-re` (aegis/, config/ with device.json `127.0.0.1:5555`, `vendor/lpa` = copies of kingdom_sweep.py + payload_reader.lua + a stub lpa_run), `logs` -> symlink to `/sdcard/Download/aegis-logs`, boot script `~/.termux/boot/aegis.sh` (wake lock, adb connect, start watchdog; the watchdog starts the bot). Start it the first time with `sh ~/.termux/boot/aegis.sh`.
7. Stop the PC copies before starting the phone ones: two bots race for the same AE_IN messages.
- Updates: `python aegis/deploy_phone.py` (PC) puts `deploy.tar` into `/sdcard/Download/aegis-ctl/`; the phone watchdog unpacks it within 30 s and restarts the bot. Other control files there: empty `restart_bot` (restart the bot only), `restart_game` (written by the bot when the game misbehaves, e.g. a covert scan with 0 ops; the watchdog force-stops + starts the game), `pause` (bot stopped while it exists). Status from the PC: `adb shell` tail of `/sdcard/Download/aegis-logs/{bot,watchdog}.log` and `bot_heart.txt` age (`$(date +%s)` minus its content).
- After a phone reboot the Wireless-debugging port is new each time: `adb mdns services` on the PC lists it (`adb-<serial>._adb-tls-connect._tcp. <phone-ip>:<port>`) even when the user cannot read it out, so try that before asking. `connect refused (10061)` on 5555 with the phone pingable = TCP mode lost = it rebooted; a stale `adb-...tls-connect` entry showing `offline` is normal. Boot reason: `getprop sys.boot.reason` (seen `reboot,rollback_staged_install()`); uptime from `uptime` dates the reboot. Termux:Boot fired on one boot and not on others: check `boot.log` before typing into Termux.
- Reboot: Termux:Boot runs the boot script, but adb-to-self needs `adb tcpip 5555` again; until then the bot is down. Recovery used 2026-11-13 (battery died, USB not detected by Windows at all): the owner turned on Wireless debugging and gave the IP:port shown (e.g. <phone-ip>:44349; the PC was already trusted, no pairing needed) -> `adb connect <ip:port>`, model check, `adb -s <ip:port> tcpip 5555`, `adb connect <phone-ip>:5555`. Same recovery 2026-11-17 (battery flat after ~4 h on the wireless charger, 'charging via NOTHING'; the owner gave port 33561; `stay_on_while_plugged_in` had reset to 0: `settings put global stay_on_while_plugged_in 7`; the game was already up when I arrived, VPN tun0 up, reader intact; one long adb shell with sleeps hung the Wi-Fi link, keep each call short); Termux:Boot did NOT fire either time (boot.log silent, no Termux process): start it by hand with `am start -n com.termux/.app.TermuxActivity`, then `input text "sh%s~/.termux/boot/aegis.sh"` + KEYCODE_ENTER (boot.log gets 'boot script ran', watchdog starts the game). A reboot after an overnight resource update also needs the reader rebuilt (`build_reader.py --install`, phone paused first so the watchdog's repair_reader does not race).

## Reader channel (bridge) rules
- The game polls `files/lpa_cmd.txt` once a second and writes `files/lpa_out.txt` in place. Every bridge (`run._raw`, the owner `lpa_run`) must: push the command as `lpa_cmd.tmp` then `adb shell mv -f` to `lpa_cmd.txt` (a non-atomic push lets the game run half a command: answers like `OK nil`); treat output starting with `cat:` as 'not written yet' (adb prints the 'No such file' error to stdout); accept an answer only when provably complete.
- Completeness: `run._raw` wraps every snippet (`_wrap`: runs it as a function, returns `tostring(value) .. '\1AEGIS_END'`) and waits for that marker; ERR answers (written by the payload, no marker) need two matching reads 0.3 s apart. Two matching reads alone are NOT enough on the phone: a half-written `OK` answer to `AE_IN.take()` (which empties the game's message queue) silently loses chat requests.
- One driver per game: the PC (Windows mutex) and the phone's Termux bot (lock file) cannot see each other's locks; both at once gives TIMEOUTs and answers belonging to the other's command. run.py on the PC refuses while the phone bot's heartbeat is fresh unless `aegis-ctl/pause` exists; the phone watchdog stops the bot while the file exists and restarts it when it is removed. A phone deploy also re-execs the phone watchdog.
- Test a bridge with deliberately slow Lua (e.g. 30 x `for i=1,4e6 do ... end`) and a burst of 40-60 quick reads counting malformed answers, not one quick command.

## Diagnosing 'Aegis is down' (in this order)
1. `adb devices` (phone: reachable over Wi-Fi?), model check, `pidof com.phs.global`. An empty list is often only the PC's adb having dropped the link: run `adb connect <phone-ip>:5555` and ping the phone before concluding it rebooted (TCP mode survives anything but a reboot).
2a. Did the messages reach the bot? Compare the listener's counter (`AE_IN.n`, messages queued since the hooks were installed) with the queries logged in bot.log: many more received than handled means requests were lost between the game's queue and the bot (incomplete reader answers), not that nobody asked. From the PC, pause the phone bot first (`aegis-ctl/pause`).
2. `logs/bot.log` tail + heartbeat age, `logs/watchdog.log` tail (it logs every dialog it sees).
3. Reader ping (`run._raw('return 1')`) and the dialog probe (`watchdog.DIALOG`): the bot can be alive with a fresh heartbeat while the game sits on a dialog.
4. `python aegis/build_reader.py --check` (venv with UnityPy): bundle md5 vs Version.txt and whether the reader is in it.
5. Screenshot (`adb exec-out screencap -p`) and `dumpsys window | grep mCurrentFocus` (a foreign popup, e.g. LDPlayer's store WebView: close with KEYCODE_BACK).
6. logcat for the game pid and `files/river_logs/RiverLog_<date>.log` (redact tokens before showing).

## Game resource updates and the reader
- Updates (often right after maintenance, sometimes on consecutive nights) restore the game's own `ABAsset/25/luascript_gameplay_hotels_game.assetbundles` and remove the reader. The game then runs normally but never answers, while the bot keeps writing its heartbeat: judge 'down' on reader silence, not only on the heartbeat.
- Rebuild with `aegis/build_reader.py --install` (Aegis's own copy; never write into the owner `lpa_alliance_fetch/gamelua`): builds from the DEVICE's current bundle (must match Version.txt's md5 = update finished), saves the pristine copy under `build/`, force-stops the game, pushes bundle + Version.txt, fixes ownership on the rooted emulator, restarts the game. `--force` rebuilds from the saved pristine copy when a bad build is installed. Dry-build first after any builder change and check the payload is present and the original script kept.
- The MiniGame TextAsset is xor-encoded (key `eyugame_lua_zombiesrpg`) and, since res 1.0.801, compiled Lua 5.4 bytecode (`\x1bLuaT`): appended source is silently ignored. Wrap instead: a source chunk `local f = assert(load("<\ddd-escaped bytecode>", "@MiniGame", "b")) local r = table.pack(f(...))` + payload + `return table.unpack(r, 1, r.n)`.
- Emulator (Android 9, sdcardfs): adb-pushed files belong to `shell` 644 and the game cannot overwrite them, which breaks the next update: `chown <game uid>:ext_data_rw` + `chmod 660` as root after every push.

## Emulator-only recovery
- Title-logo hang after a PC/LDPlayer restart (logcat `GraphicBufferAllocator: Failed to allocate`, Unity stops after `eglCreateContext`, reader silent): start with OpenGL ES forced: `am start -n com.phs.global/com.games37.sdk.AtlasPluginDemoActivity -e unity -force-gles30`. Low free host RAM (big local models, ComfyUI) makes it worse.
- An LDPlayer restart can reset the instance's cpu/RAM/resolution; the game runs at the defaults.

## Watchdog (aegis/watchdog.py, start_watchdog.ps1)
Every 30 s, first problem wins: device reachable (phone: `adb connect`, else re-enable TCP via USB; emulator: `ldconsole launch`) -> model -> game pid -> phone: screen awake, game in front, battery/heat warning -> bot process -> dialogs (table above) -> heartbeat stale OR reader silent 5 min -> `repair_reader()` (build_reader --check/--install) before force-restarting the game. Caps per hour: 3 game, 6 bot, 12 presses, 2 reader rebuilds. Stays hands-off while the owner tools run. Test new branches offline by stubbing `sh/adb/pythons/R._raw/time.time` and stepping `tick()` (or `dialog()` with a fake `run` module in `sys.modules`); the class is `Dog`.
- Any box the watchdog only logs ('not a plain reconnect box, leaving it') is an outage in waiting: when one appears in the log, add a table row + branch for it the same day.
- After a deploy the watchdog re-execs itself (same PID, `ps` still shows `python aegis/watchdog.py`) and can take ~3 min before 'watchdog started'; the bot is down until its first pass. Wait for that line before treating it as hung.
- The phone gets warm on a wireless charger during long shield runs (~43 C; the watchdog warns at 45 C): suggest the cable or airflow before a long event.
